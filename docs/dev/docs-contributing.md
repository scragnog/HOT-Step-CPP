# Writing and maintaining the docs

The docs live in this repo, under `docs/`, so they version with the code. A code change
that alters behaviour a user or developer can see is not finished until the matching page
is updated. The ownership table in [AGENTS.md](../../AGENTS.md#documentation-is-part-of-the-change)
says which page each source area owns, and `node tools/docs/check-docs.mjs` fails when a
studio has no page, a generated table is stale, or a link is broken.

## Layout

| Path | Audience | Contents |
|---|---|---|
| `README.md` | everyone | Landing page: what it is, download, quick start, gallery, links into docs |
| `FEATURES.md` | users | One line per feature, each linking to the page that explains it |
| `docs/README.md` | everyone | Index of every page |
| `docs/user/` | users | Getting started, backends, generation, one page per studio, adapters, plugins, training, quality, troubleshooting |
| `docs/dev/` | contributors and agents | Architecture, engine, API, config, building, plugin authoring, training internals, releasing, writing style |
| `.claude/skills/` | agents | Procedures for maintenance tasks (see its README) |
| `docs/plans/` | local only | Gitignored design notes. Distil lasting decisions into `docs/dev/` |

Generated files carry a `<!-- generated by tools/docs/build-docs.mjs -->` line. Edit the
source they are built from, then run `node tools/docs/build-docs.mjs`. They are:

- `docs/user/plugins.md` tables (from the metadata block in each `engine/plugins/**/*.lua`)
- `docs/dev/api.md` (from `router.<verb>(` calls in `server/src/routes` and the mounts in `server/src/index.ts`)
- `docs/user/models.md` (from `server/src/data/model-registry.json`)
- the marked blocks in `server/src/data/assistant-knowledge.md` (from `docs/user/`)

## Rules for every page

Follow [writing-style.md](writing-style.md): sentence case headings, no emojis, no em
dashes, no puffery, straight quotes.

Document only what you can verify in the code, the UI strings (`ui/src/i18n/locales`), or
by running it. Never describe what a control probably does. If you cannot tell, name the
control and where it lives, and leave `<!-- TODO(verify): ... -->` for someone who can.

No artist names, album names or dataset names from private collections. Generic examples
only ("a 90s trip-hop album", not a real one).

Relative links only, to the file: `[Cover Studio](studios/cover-studio.md)`. Anchors are
lowercase-hyphenated heading text.

Screenshots go in `docs/images/` as `.webp`, named `studio-<slug>.webp`. Until the image
exists, keep the image line and a `<!-- screenshot: needed -->` comment so the gap is visible.

## Studio page template

```markdown
# <Sidebar name>

<One paragraph: what it is for and when to reach for it.>

![<Sidebar name>](../../images/studio-<slug>.webp)
<!-- screenshot: needed -->

## Where to find it

Sidebar entry, and anything that has to be true first (a backend, a model, a song in the library).

## Workflow

1. Numbered steps for the common path, in the order the UI presents them.

## Controls

| Control | What it does |
|---|---|
| Label as shown in the UI | One or two sentences. Ranges and defaults where they matter. |

## Tips and limits

Short prose or bullets: what trips people up, what the studio does not do.

## Related

- [Other page](../other-page.md)
```

Keep a studio page between 60 and 250 lines. If it needs more, the studio has a
sub-feature that wants its own page.

## Checking

```
node tools/docs/build-docs.mjs      # refresh generated tables
node tools/docs/check-docs.mjs      # exit 1 on drift or broken links
```

Both run inside `node server/scripts/check-release-prereqs.mjs` and in CI.
