# Model files

Every model the app can download is listed in the registry at
`server/src/data/model-registry.json`. The [Model Manager](studios/model-manager.md) reads the
same file, so what you see there is what is listed here, minus what your build cannot use:
it hides CUDA-only files and packs on the Vulkan, ROCm and CPU builds, Windows DLLs on Linux
and macOS, and the runtime pack for the other CUDA version. The tables below are generated
from the registry by `node tools/docs/build-docs.mjs`; edit the registry, not this page.

Roles: `dit` is the diffusion transformer that renders audio, `lm` is the language model
that plans the song, `vae` decodes latents to audio, `embedding` is the ACE-Step text
encoder and `pp-vae` the post-processing decoder. `mm3` and `yue2` mark the files of those
backends, and `stablestep` the Stable Audio 3 files that its backend, its training and the
StableStep refiner use.
`supersep` is stem separation, `whisper` transcription, `moss` local captioning and
`runtime` the runtime libraries. A quant label such as `Q8_0` or `Q4_K_M` is the GGUF
quantisation; lower numbers mean smaller files and less VRAM at some cost in quality.
[Getting higher quality output](quality.md) explains which precision to pick for each backend.

Files download from Hugging Face into the models folder: `models/` in the data folder in a
release (see [Data folder and upgrades](data-folder.md)), or wherever **Models directory** in
Settings points. MiniMax-Music3, YuE2, MOSS, Music Flamingo, stem separation and Whisper files go in its
`mm3/`, `yue2/`, `moss/`, `flamingo/`, `supersep/` and `whisper/` subfolders, and the Stable Audio 3
tokenizer files in `onnx/sa3/`. In a release, runtime libraries go to the data folder's
`tools/runtime/`; a git checkout keeps them next to the engine binary. A new extracted version
reuses all of them through the saved data folder location.

You can also drop your own ACE-Step GGUF files directly in the models folder. The engine
picks up any file whose architecture it recognises when it next starts, and it appears in
the model dropdowns. The Model Manager lists only catalogue files.

YuE2 cover transcription uses the optional SheetSage2 model. If it cannot load
alongside the generation engine, an active render finishes first; transcription
then retries once with the engine paused. The engine restarts before queued renders
continue. Supplying an approved ABC score skips the transcriber.

SheetSage2-Refined (`yue2-sheetsage2-refined-f16`, 156 MB) is an optional
alternative transcriber. Choose it under the YuE2 **Models** dropdown >
**Lead-sheet transcriber**. The choice applies everywhere SheetSage runs: cover
transcription, the YuE2 AR sheet stage and labelling (key source and `.abc` sidecars).
Lead sheets already cached keep the transcriber that wrote them until you transcribe
again. It reuses SheetSage2's encoder, so SheetSage2 must be
installed as well. It reads odd meters and meter changes, slash chords and
tension chords, and with **Keys with modes** on it writes modal keys such as
`K:Ddor`. It is anime-song's fine-tune of SheetSage2, CC BY-NC 4.0: non-commercial
use only.

SA3 adapter training uses the separate Medium Base BF16 checkpoint and its own
embedded conditioner. Keep the distilled generation weights installed. The SA3
training pack also includes the SAME encoder and T5Gemma text encoder. The base's
quantized variants are experimental and are not supported training bases. Their
audible quality has not been verified by listening.

The SA3 base quants preserve learned memory tokens and conditioner weights at
their original precision, as required by the loaders. Variants marked `-imat`
use activation statistics from 12 forwards of the BF16 base on three captured
training clips with synthetic audio. This small calibration set does not establish
music-domain quality. The quantized generation DiTs keep the same tensors at original
precision and are experimental too: BF16 remains the default generation model, and their
`-imat` variants were calibrated on 12 forwards with synthetic reference clips. To reproduce
the ladder from the engine directory, run
`bash quantize.sh <model-BF16.gguf> <imatrix.gguf>` with the existing quantizer built.
The script also accepts the BF16 path alone for the uncalibrated K/FP4 ladder.
Completed files appear only after quantization succeeds; interrupted `.partial`
files are retried on the next run.
The existing quantizer's S/M/L presets produce identical tensor encodings within
the SA3 Q3, Q4 and Q5 groups; those names do not indicate different quality here.
